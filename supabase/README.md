# Premium backend — deployment notes

## Current state: there is no backend

The project ref configured in `config.toml` and in the app's Supabase client is:

```
pqrnobnniqfxysztjrgo
```

That subdomain **does not exist**. It returns NXDOMAIN from both the Cloudflare
resolver and Google's:

```
$ curl -s "https://cloudflare-dns.com/dns-query?name=pqrnobnniqfxysztjrgo.supabase.co&type=A" \
    -H "accept: application/dns-json"
{"Status":3, ...}
```

`Status: 3` is NXDOMAIN. A randomly invented ref returns the identical response,
which is how you can tell a deleted project from a paused one — a paused project
still resolves and serves a wake-up page.

Practical consequences:

- `supabase.functions.invoke(...)` from the browser cannot succeed. Every call
  fails at DNS.
- The edge functions in this directory have never run in production.
- The Supabase client in `src/integrations/supabase/client.ts` also carries a
  24-character value where an anon JWT belongs. That file is generated by the
  host platform and was almost certainly scrubbed when the repo was exported,
  so the real key may exist in the deployed bundle — but it does not matter
  while the host does not resolve.

Nothing in the app hard-depends on any of this. See `src/lib/premiumApi.ts`:
checkout falls back to the Stripe payment link, and entitlement verification is
treated as an enhancement that may fail.

## What still works without a backend

The Premium Edition PDF is generated entirely in the browser, so delivery needs
no server. A buyer who completes checkout and lands on `/payment-success`
receives their file today.

## To bring the backend up

1. **Create the project.** In the Supabase dashboard, create a project and copy
   its ref. Update all three places the old ref appears:
   - `supabase/config.toml` → `project_id`
   - `src/integrations/supabase/client.ts` → `SUPABASE_URL` and the publishable key
   - `.env` → `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`,
     `VITE_SUPABASE_PROJECT_ID`

2. **Run the migration.** It creates `entitlements`, enables RLS with *no*
   policies (so only the service role can touch it), and adds the
   `touch_entitlements_updated_at` trigger.

   ```
   supabase db push
   ```

3. **Set the secrets** the functions read:

   ```
   supabase secrets set STRIPE_SECRET_KEY=sk_live_...
   supabase secrets set STRIPE_WEBHOOK_SECRET=whsec_...
   supabase secrets set SITE_URL=https://blueprint.mysticaldigits.com
   ```

   `SITE_URL` matters: without it `create-payment` falls back to the request's
   `Origin` header, which any caller can set.

4. **Deploy the functions.**

   ```
   supabase functions deploy create-payment
   supabase functions deploy verify-entitlement
   supabase functions deploy stripe-webhook --no-verify-jwt
   ```

   `stripe-webhook` must skip JWT verification — Stripe cannot present a
   Supabase token. It authenticates by verifying the Stripe signature against
   the raw body instead, and it is the only thing that writes an entitlement.

5. **Register the webhook** in the Stripe dashboard at
   `https://<ref>.supabase.co/functions/v1/stripe-webhook`, subscribed to
   `checkout.session.completed` and `charge.refunded`.

6. **Point the payment link at the success page.** The checkout in production is
   a Stripe payment link, not `create-payment`. In the Stripe dashboard, set
   that link's confirmation/redirect URL to
   `https://blueprint.mysticaldigits.com/payment-success`.

   Payment links do not reliably template `{CHECKOUT_SESSION_ID}` onto the
   redirect, which is why `/payment-success` also grants on arrival rather than
   requiring a session id. Once the backend is live you may prefer to route
   checkout through `create-payment`, which does return a session id and
   therefore allows real server-side verification.

## How entitlement is decided

`resolveEntitlement()` in `src/lib/entitlement.ts` resolves in this order:

| Evidence | Result |
| --- | --- |
| `verify-entitlement` confirms the session or email | granted, `source: "server"` |
| Arrival on `/payment-success` | granted, `source: "stripe-redirect"` |
| `md:premium-unlocked` in localStorage | granted, `source: "local"` |
| Nothing | refused |

The lower tiers exist on purpose. The failure modes are not symmetric: refusing
a real buyer leaves someone who paid with nothing, while admitting a faker costs
a $7.99 sale they were never going to complete. A backend outage should not be
able to lock a paying customer out of their own file.

The residual hole is that localStorage can be set from devtools. Closing it
properly means gating the *content* rather than the delivery, which means moving
generation server-side. For this product that is not worth the complexity — but
the decision is recorded here rather than left implicit.
